# The test corpus

The binary fixtures under `crates/unrar-rs/tests/fixtures/` and
`crates/par2-rs/tests/fixtures/` are the **test corpus**: 371 archives, parity
sets, SFX modules, video inputs and originals that the unit, integration, slow,
PAR2, UnRAR, wasm and CLI suites read. They are published as a signed,
content-addressed object set on Cloudflare R2 and hydrated by `xtask`; Git LFS
is the legacy transport and is removed once a published corpus is pinned (see
[Migration](#migration)).

The corpus is **independent of the benchmark corpus** in
`bench/rarpar-bench`: the two share generator code and the pinned toolchain
lock, but never a manifest, an output, a bundle identity, or a regeneration
schedule. No benchmark output is ever a test fixture, and no test fixture is
regenerated by a benchmark run.

## Files in the repository

| Path | Role |
| --- | --- |
| `test-corpus/sources.json` | Provenance ledger. One entry per fixture path: size, SHA-256, and its **source**: `generated` (which generator script, which pinned writer/encoder/parity tool, which inputs), `upstream` (which pinned upstream commit and path, under which license), or `blocked` (provenance incomplete). |
| `test-corpus/profiles.json` | Named subsets of the corpus, as path globs, one per hydration need (`unit`, `cli`, `unrar`, `par2`, …). |
| `test-corpus/lock.json` | The one published manifest CI and developers hydrate from: its SHA-256, its public URL, the Sigstore identity that must have signed it, and the commit it was published from. |
| `bench/rarpar-bench/config/toolchains.json` | The shared generator-toolchain lock: the six RARLAB writers (3.93, 4.20, 5.00, 6.24, 7.20, 7.23), the digest-pinned FFmpeg 7.1 encoder image, and the par2cmdline-turbo generator, each pinned by URL and SHA-256. Frozen from Renovate; a toolchain change is a deliberate corpus revision. |
| `.github/workflows/test-corpus-publish.yml` | The protected, manual, `main`-only workflow that reconstructs, validates, packages, signs and uploads a corpus revision. Implementing it does not dispatch it. |

### `sources.json`

```json
{
  "schema_version": 1,
  "toolchains": "bench/rarpar-bench/config/toolchains.json",
  "generators": {
    "generate_edge_cases.sh": {
      "path": "crates/unrar-rs/tests/fixtures/generate_edge_cases.sh",
      "toolchains": ["rarlab-6.24", "rarlab-7.20"],
      "byte_reproducible": false,
      "notes": "…"
    }
  },
  "upstreams": {
    "junrar": {
      "repository": "https://github.com/junrar/junrar",
      "commit": "<40 hex>",
      "license": "LicenseRef-UnRAR",
      "license_path": "LICENSE",
      "encoding": "raw"
    }
  },
  "files": [
    {"path": "crates/unrar-rs/tests/fixtures/rar5/rar5_multifile_store.rar", "size": 721, "sha256": "…", "format": "rar5",
     "source": {"kind": "generated", "generator": "generate_edge_cases.sh", "toolchains": ["rarlab-7.20"], "inputs": ["crates/unrar-rs/tests/fixtures/originals/hello.txt"], "notes": "…"}},
    {"path": "crates/unrar-rs/tests/fixtures/rar4/rar15_lz.rar", "size": 91234, "sha256": "…", "format": "rar15",
     "source": {"kind": "upstream", "upstream": "junrar", "path": "src/test/resources/…/BoatModernEnglish-regular-unpack15-dos.rar"}},
    {"path": "…", "size": 1, "sha256": "…", "format": "rar5", "source": {"kind": "blocked", "reason": "…"}}
  ]
}
```

`format` labels the container (`rar15`, `rar20`, `rar4`, `rar5`, `rar4-rev`,
`rar5-rev`, `sfx-rar4`, `sfx-rar5`, `par2`, `mkv`, `wav`, `bin`, `tar.gz`); the
era profiles are checked against it. A generated entry's `toolchains` are the
lock ids its generator step invokes on the pinned toolchain — the regeneration
toolchain. Where the checked-in bytes predate a pin (a clip from an unpinned
host ffmpeg, a `.par2` from par2cmdline 1.1.1, an archive from an unrecorded
writer image), the entry's `notes` say so; nothing claims a writer it cannot
prove, and the generator's `byte_reproducible` flag says whether re-running it
could ever reproduce the bytes.

Rules the tooling enforces:

- Every fixture path the tests can read is listed exactly once, and every
  listed path exists in the tree with the recorded size and SHA-256. A Git LFS
  pointer where bytes should be is an error, never a skip.
- A `generated` source names a generator that exists in the tree and only
  toolchain ids that exist in the toolchain lock and that its generator
  declares. A generated file in a tool-written format names at least one
  toolchain unless its generator is a hand-assembler (no toolchain,
  byte-reproducible). The RAR 1.5 and 2.0 junrar archives are `upstream`
  imports and are never assigned a RARLAB writer.
- An `upstream` source names a pinned commit (never a branch), an upstream
  path, and a license. The publish workflow re-fetches every public upstream
  file at that commit (`verify --upstreams`; libarchive's uuencoded archives
  are decoded first) and requires byte identity. Private upstreams (the Scryer
  e2e release gate, and weaver — the repository this corpus was ported from,
  which is where the sets that have no generator step in either tree come
  from) are pinned by commit and Git LFS oid and verified from the checkout.
- A `blocked` entry blocks publication. Nothing with incomplete provenance is
  seeded into R2, however long it has sat in LFS.
- Generated fixtures are **shape-reproducible, not byte-reproducible**: RAR
  stamps times into headers, encryption draws random salts, and some inputs
  were drawn from `/dev/urandom` or an unpinned encoder. The published bytes are
  therefore the canonical fixtures; the generator and writer are recorded so a
  future revision can be regenerated on the pinned toolchain, and regeneration
  is always a new corpus revision, never an in-place replacement.

### `profiles.json`

A profile (a *bundle*) is a named subset of the corpus: what one CI lane or one
developer task hydrates. The RAR fixtures are bundled by **format era**, which
is how the UnRAR lanes are split:

| Profile | Contents |
| --- | --- |
| `rar12` | RAR 1.5 / 2.0 archives (the junrar oracle imports) and their expected output |
| `rar34` | RAR 2.9-format archives — everything written by RAR 3.x/4.x writers (`rar4/`, minus the RAR 1.5/2.0 imports) |
| `rar57` | RAR5-format archives — everything written by RAR 5.x/7.x writers (`rar5/`) |
| `unrar` | `rar12` ∪ `rar34` ∪ `rar57` (all of `crates/unrar-rs/tests/fixtures/`) |
| `par2` | all of `crates/par2-rs/tests/fixtures/` |
| `unit` | the two fixtures the no-fixture unit lanes read |
| `cli` | what the CLI smoke lane reads |
| `wasm-unrar` | exactly the fixture families the wasm UnRAR harness opens |
| `release-tests`, `ppmd-perf` | the subsets `release.yml` and `ppmd-perf.yml` hydrate |
| `all` | everything |

Every RAR-era profile also carries `originals/**` (the extracted-output
oracles the integration tests compare against), so an era lane is
self-sufficient.

```json
{
  "schema_version": 1,
  "profiles": {
    "rar12": {"include": ["crates/unrar-rs/tests/fixtures/rar4/rar15_lz.rar", "crates/unrar-rs/tests/fixtures/rar4/rar20_*.rar", "crates/unrar-rs/tests/fixtures/originals/**"]},
    "rar34": {"include": ["crates/unrar-rs/tests/fixtures/rar4/**", "crates/unrar-rs/tests/fixtures/originals/**"],
              "exclude": ["crates/unrar-rs/tests/fixtures/rar4/rar15_lz.rar", "crates/unrar-rs/tests/fixtures/rar4/rar20_*.rar"]},
    "rar57": {"include": ["crates/unrar-rs/tests/fixtures/rar5/**", "crates/unrar-rs/tests/fixtures/originals/**"]},
    "unrar": {"include": ["crates/unrar-rs/tests/fixtures/**"]},
    "par2":  {"include": ["crates/par2-rs/tests/fixtures/**"]},
    "unit":  {"include": ["crates/unrar-rs/tests/fixtures/rar5/rar5_hp_store.rar", "crates/unrar-rs/tests/fixtures/rar4/rar4_hp_large.rar"]},
    "cli":   {"include": ["crates/unrar-rs/tests/fixtures/rar5/rar5_store.rar", "crates/par2-rs/tests/fixtures/rar5_lz_plain/**"]}
  }
}
```

A profile resolves to the sorted list of ledger paths matching any `include`
glob and no `exclude` glob; the manifest records the resolved lists so a fetch
never re-derives membership from the working tree, and the build refuses a
profile that resolves to nothing. Profiles are additive on the command line
(`--profile rar34 --profile rar57`). Because objects are content-addressed
per file, overlapping profiles cost nothing extra to store or publish.

### `lock.json`

```json
{
  "schema_version": 1,
  "base_url": "https://<public R2 domain>",
  "manifest": {"sha256": "<hex>", "url": "https://<public R2 domain>/test-corpus/manifests/sha256/<hex>.json"},
  "signature": {
    "bundle_url": "…/<hex>.json.sigstore.json",
    "certificate_identity": "https://github.com/scryer-media/rarpar/.github/workflows/test-corpus-publish.yml@refs/heads/main",
    "certificate_oidc_issuer": "https://token.actions.githubusercontent.com"
  },
  "provenance": {"sha256": "<hex>", "url": "…/<hex>.provenance.json"},
  "published_from": {"commit": "<40 hex>", "run": "https://github.com/scryer-media/rarpar/actions/runs/<id>"}
}
```

An empty `manifest.sha256` means no corpus has been published yet; `fetch`
refuses to run and CI keeps hydrating from LFS until the lock is populated.

## The published objects

Every object is immutable and content-addressed; a bucket key is never
rewritten, and every historical manifest and every object any manifest
references is retained.

| Key | Content |
| --- | --- |
| `test-corpus/objects/sha256/<hex>` | One fixture's bytes. Shared by every corpus revision that contains the same bytes, so a revision that changes one fixture uploads one object. |
| `test-corpus/manifests/sha256/<hex>.json` | A manifest, addressed by its own SHA-256. |
| `test-corpus/manifests/sha256/<hex>.json.sigstore.json` | The Sigstore bundle `cosign sign-blob` produced for that manifest under the publish workflow's OIDC identity. |
| `test-corpus/manifests/sha256/<hex>.provenance.json` (+ `.sigstore.json`) | Build metadata for that manifest: source commit, workflow run, actor, timestamp, toolchain lock digest. Signed the same way. |
| `tools/rarlab/sha256/<hex>/<archive>` (+ `.sigstore.json`, `provenance.json`, `provenance.json.sigstore.json`) | An original, unmodified RARLAB distribution archive mirrored by the same workflow, with its signed provenance (official URL, SHA-256, size, mirroring run). `tools/par2cmdline-turbo/…` follows the same shape. |

### The manifest

The manifest is a **pure function** of `sources.json`, `profiles.json` and
`toolchains.json`: canonical JSON (sorted keys, no insignificant whitespace,
paths sorted). It carries every file's path, size, digest, source group,
generator, and toolchain identifiers; the resolved profile lists; the
generator and upstream tables; and the toolchain lock's digest and pinned
sources. It carries **no** build metadata, so anyone can recompute it from a
checkout and compare its digest to the lock: `xtask test-corpus verify` does
exactly that, offline.

## Verification chain

```
git commit ──► test-corpus/lock.json ──► manifest.sha256 ──► manifest.json ──► file sha256 ──► object bytes
                                    └──► Sigstore bundle: cosign verify-blob
                                         --certificate-identity <publish workflow @ refs/heads/main>
                                         --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

- `fetch` always verifies the manifest against the locked digest and every
  object against its manifest digest before it writes anything into the tree.
  Files are written atomically (temp file, rename) at their repository paths.
- `verify` recomputes the manifest from the tree and requires it to match the
  lock (so a ledger edit without a republish fails closed), checks every
  present fixture against the ledger, and — with `--require-signature` or when
  `cosign` is present — verifies the Sigstore bundle's signature, exact
  workflow identity, and issuer. The fixture-tests lane runs it with
  `--all-present --require-signature`; while nothing is pinned the flag is a
  no-op, and it bites the moment a manifest is.
- The tool-source mirror in the benchmark harness fails closed: an object that
  is present on R2 but has a wrong digest, an invalid signature, a signer other
  than the publish workflow, or provenance that disagrees with the lock is an
  error. It is neither replaced nor silently bypassed; only *absence* (HTTP
  404) or retry-exhausted unavailability falls back to the official RARLAB URL,
  and that download must still match the reviewed SHA-256 before it is used.

## Commands

```sh
# What CI and developers run before Cargo: fetch from the pinned corpus, or —
# while the lock pins nothing — a verified `git lfs pull` of the same profiles.
# Fails when anything is missing, still a pointer, or has the wrong digest.
cargo run --locked -p xtask -- test-corpus hydrate --profile rar34 --profile rar57
cargo run --locked -p xtask -- test-corpus hydrate --profile unit

# Fetch from the pinned published corpus only (what hydrate becomes once pinned)
cargo run --locked -p xtask -- test-corpus fetch --profile unrar

# Check a checkout: ledger vs tree vs lock, the published manifest and its
# signature (cosign), and with --upstreams every public import re-fetched
cargo run --locked -p xtask -- test-corpus verify [--all-present] [--require-signature] [--upstreams] [--offline]

# Build a manifest, its digest and provenance from the tree
cargo run --locked -p xtask -- test-corpus build --out target/test-corpus/build
# (--update-ledger refreshes sizes/digests of paths already in the ledger)

# Sign manifest + provenance keyless with cosign, then upload everything
# (publish workflow only)
cargo run --locked -p xtask -- test-corpus sign --dir target/test-corpus/build
cargo run --locked -p xtask -- test-corpus publish --dir target/test-corpus/build \
    --base-url https://<public R2 domain> --s3-endpoint https://<account>.r2.cloudflarestorage.com --bucket <bucket>

# Shared pinned encoder for the corpus's video inputs
cargo run --locked -p xtask -- bench payload video --profile ffmpeg-video --target-bytes 1100000 --out /tmp/clip.mkv

# Resolve (and, in the workflow, mirror) the toolchain source archives
cargo run --locked -p xtask -- bench toolchains resolve --mirror-base https://<public R2 domain>
```

`fetch` and `publish` speak HTTP through `curl` (already required by the
harness's Docker builds and present on every CI runner). `publish` uses curl's
native SigV4 (`--aws-sigv4 aws:amz:auto:s3`) against the R2 S3 endpoint with
`If-None-Match: *`, so a key is created at most once; a `412 Precondition
Failed` is followed by a public read-back that must match the digest, and any
mismatch aborts the publication. Publishing a manifest that is already published is an
idempotent re-verification: its objects are read back, the first publication's
provenance and signatures are kept, and the printed lock entry names that first
publication. Signatures come from `cosign` (keyless, GitHub
OIDC); no crypto is implemented in this repository for the corpus.

## The publish workflow

`test-corpus-publish.yml` is `workflow_dispatch` only, refuses any ref other
than `refs/heads/main`, runs in a protected environment, and is the only place
that holds R2 write credentials. Its steps:

1. Check out `main`, hydrate every fixture (LFS while it lasts, else `fetch`),
   and run `test-corpus verify` against the ledger — every path, no `blocked`
   entries.
2. Re-fetch every public upstream import at its pinned commit and require byte
   identity (junrar, libarchive, ssokolow, par2cmdline-turbo; the private
   Scryer e2e imports are pinned by commit and LFS oid and are verified from
   the checkout).
3. Build and mirror the toolchain sources: resolve each RARLAB archive
   R2-first, fall back to RARLAB, verify the reviewed SHA-256, sign and
   conditionally upload the unmodified tarball and its provenance, read back.
4. `test-corpus build` → manifest; `cosign sign-blob` → bundles for manifest
   and provenance; `test-corpus publish` → objects, manifest, provenance,
   bundles.
5. Print the lock entry to paste into `test-corpus/lock.json`. **The workflow
   never creates a branch, commit, or PR**; pinning the new manifest is a
   reviewed PR that must pass CI from a clean checkout.

Configuration the workflow reads (repository/environment settings, not the
tree): secrets `R2_CORPUS_ENDPOINT` (the bucket's S3 endpoint,
`https://<account>.r2.cloudflarestorage.com`), `R2_CORPUS_S3_ACCESS_KEY` and
`R2_CORPUS_S3_SECRET` (the S3 credential pair of an R2 API token with Object
Read & Write on the corpus bucket), and variables `R2_CORPUS_BUCKET` and
`R2_CORPUS_PUBLIC_URL` (the public read domain, also recorded in `lock.json`).
Both publishers read the pair from `R2_CORPUS_ACCESS_KEY_ID` /
`R2_CORPUS_SECRET_ACCESS_KEY` in the environment; nothing is derived or
echoed. The job runs in the `test-corpus-publish` environment, which is where
the secrets live and where required reviewers are set. A `dry_run` input
reconstructs, verifies, builds and signs without uploading.

## Migration

1. Land the tooling with an empty lock. Every CI lane already hydrates through
   `test-corpus hydrate --profile …`, which — with nothing pinned — pulls the
   same profiles through Git LFS and verifies them against the ledger.
2. An operator dispatches the publish workflow from `main`. It publishes the
   first corpus revision and prints the lock entry.
3. A reviewed PR pins that manifest in `lock.json`. From that commit on,
   `hydrate` fetches from R2 instead of LFS, in every lane, with no other CI
   change; the PR must pass from a clean checkout **without Git LFS**.
4. Only after that PR is merged are the LFS pointers, `.gitattributes` rules
   and LFS hooks removed, in a follow-up that also proves a fresh clone without
   `git-lfs` can hydrate and validate every profile.

## Regenerating fixtures

Generated fixtures are regenerated only as a corpus revision: run the
generator on the pinned toolchain (`xtask bench toolchains build` builds the
`rarpar-bench-rarlab:<version>` images from the mirrored, digest-verified
RARLAB archives; video inputs come from `xtask bench payload video`), update
`sources.json` (`test-corpus build --update-ledger` refreshes sizes and
digests of paths already in the ledger; provenance is edited by hand), publish,
and pin. Never use `unrar` — the binary or its source — to author, stamp or
complete a fixture; RARLAB writers, real archives, and fully self-computed
bit assembly are the only legitimate sources.
